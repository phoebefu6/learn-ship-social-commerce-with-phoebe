Building the metric registry

Three people asked for "GMV" and got three numbers. That is not a reporting problem, it is a definitions problem, and it has a cheap fix: write each metric once, as a function, with a test, and make every report import it. Tonight you build that registry for Serai Commerce, the constructed enabler whose exports hold 8,614 real Olist orders. You compare it against a naive sum and an independent reference, watch it agree to 100.00% where the naive GMV reaches 85.04%, and then feed it dirty rows to see what a definition cannot do.

Part 1 · covers orders, GMV and repeat rate as written definitions

One definition each

6 min live

A metric definition has three parts: what is counted, what is left out on purpose, and the grain it counts at. Write all three down. The part people skip is the second one, and it is where most disagreements live: freight in or out, re-sends counted once or twice, a person or a per-order id.

LiveThe three definitions, with what each leaves out4 min▶
MetricCountsLeaves out, on purposeGrainSerai, repaired

GMVsum of item price, BRLfreight; refunds sit in a separate adjustments table after session 2's quarantineline, summedBRL 1,197,842.24
repeat ratecustomers with 2 or more distinct orders, divided by all customersper-export customer keys; the resolved person key is the only one usedresolved person3.00% (250 / 8,333)

None of these choices is the only correct one. Plenty of teams report GMV with freight, and that is a fine metric if it is called something else and defined once. What breaks trust is two definitions sharing one name. Store GMV in integer cents behind the function (119,784,224 cents for Serai) so "agrees to the cent" is an equality test, not a tolerance.

LiveWhy a function, not a SQL snippet in a wiki2 min▶

A definition written in prose drifts the first time someone retypes it. A definition written as a function can be imported, tested and versioned: a change shows up in review, and a test fails if the change was an accident. The registry is small on purpose. Three functions with docstrings and tests are worth more than forty metrics nobody owns.

★ The shape of one registry entrydef repeat_rate(o): """Repeat rate: customers with 2+ distinct orders / customers. Grain: resolved person (customer_key from the identity gate). Leaves out: per-export customer keys.""" ...
Real world

The repeat rate that reads zero. Olist ships two customer columns: a customer_id that is new on every order, and a customer_unique_id for the person behind it. Key the repeat-rate definition on the first and the full public file reports 0.00% repeat customers, because no per-order id ever orders twice. Key it on the second and it reports 3.00%. Same rows, same formula, a different grain written in one argument. That is why the grain belongs in the docstring.

Part 2 · covers the registry against a naive sum and an independent reference

Registry, naive, reference

6 min live

A registry earns trust by agreeing with something it did not compute. Serai's reference totals come from the data builder, in pandas, straight from the source rows: a separate code path. The registry runs on the repaired exports. The naive sum is what someone gets by adding up the raw files. Put all three side by side and the definitions do the talking.

Agreement here is the smaller value divided by the larger, so 100.00% means identical and the measure is the same whichever side is high. Notice the directions: naive orders read high (re-sends), naive GMV reads high (freight and refund lines), naive repeat reads low (8,506 export-local customer keys instead of 8,333 people, so cross-export repeat buyers vanish). A single "within 2%" check would pass orders and miss GMV. Check each metric on its own.

Self-studyWhy 100.00% is a measurement, not a tautology2 min▶

It is tempting to read the registry's 100.00% as "it agrees with itself". It does not. The reference was computed by the data builder from the source rows, before the constructed defects were added; the registry runs on the exports after session 2's repair. Agreement to the cent says the repair restored the source exactly and the definitions match the reference's. Miss one repair rule and this number drops, which is the point of keeping a second code path. Serai's constructed gate asks for 99.5% agreement on every metric before the registry goes live; session 10 shows the gate switching the registry off.

Real world

Freight lives on the line. In the Olist files freight is charged per item, beside the item price, and one order can hold items from several sellers. Add price and freight across the full public delivered set and you get BRL 15,419,773.75 against BRL 13,221,498.11 of item price: 85.74% agreement before a single dirty row is involved. A definition gap alone moves GMV by double digits.

Part 3 · covers the registry run on unrepaired rows

The registry on dirty rows

5 min live

Now skip session 2. Run the same registry, unchanged, on the raw exports. Two numbers barely move and one breaks: the repeat rate reads 4.61% instead of 3.00%, and the registry's agreement falls to 65.14%. The definition did nothing wrong. It counted exactly what it was given.

LiveWhy a definition cannot fix a bad row3 min▶

A re-send arrives under a variant key that normalisation cannot recognise, for the same customer, on the same day. To the registry it is a second order, so the customer becomes a repeater: 384 repeat customers instead of 250, a 4.61% repeat rate on 8,337 keys. You could try to patch the definition ("ignore a second order on the same day") but Olist has real same-day repeat orders, 83 of the 197 orders in the sample followed by another within 90 days, so that patch would delete real behaviour to hide a pipeline fault. The right fix sits one layer down: session 2's key test catches the re-send and drops it before any metric sees it.

The other two metrics look healthy on dirty rows (orders 98.27%, GMV 99.03%), which is the trap. Report the minimum agreement across metrics, not the average: averaging would put this registry around 87% and hide that one number is more than half again too high.

The split matters for ownership: if the registry team starts absorbing pipeline faults into definitions, the definitions stop meaning what their names say.

Real world

Same-day repeats are real in Olist. Of the 197 orders in Serai's sample followed by another order within 90 days, 83 happened on the same day. Some are split checkouts, some are genuine second purchases, and the data does not say which. A re-send looks exactly like them. Session 4 takes up that ambiguity; tonight the lesson is that the registry should not guess.

Build-along

Three functions, three tests, one run

★ 22 min · everyone builds

Download the public dataset with kagglehub.dataset_download("olistbr/brazilian-ecommerce") (no login needed) and work in a scratch folder. The registry and its tests come first, on frames small enough to check by eye; only then does it touch the real file. The printed outputs below are what the code prints on the full public file.

Write the registry: three functions, each with its definition in the docstring. Save it as registry.py. Every report imports from here.

★ Block 1 · registry.pyimport pandas as pd def orders(o): """Orders: distinct normalised order keys.""" return o["order_key"].str.strip().str.lower().nunique() def gmv(li): """GMV: sum of item price, freight excluded, in BRL.""" return round(li["price"].sum(), 2) def repeat_rate(o): """Repeat rate: customers with 2+ distinct orders / customers. Grain: the resolved person key, never a per-order id.""" per = o.assign(k=o["order_key"].str.strip().str.lower()).groupby("customer_key")["k"].nunique() return (per >= 2).sum() / len(per)

Pin each definition with a test on a frame small enough to check by eye. These are plain asserts in test_ functions, so any Python test runner collects them; the loop at the bottom runs them without one. The frames are constructed.

★ Block 2 · tests (constructed frames)def test_resend_counts_once(): o = pd.DataFrame({"order_key": ["A1", "a1 ", "B2"], "customer_key": ["c1", "c1", "c2"]}) assert orders(o) == 2 def test_gmv_excludes_freight(): li = pd.DataFrame({"price": [10.0, 5.5], "freight_value": [3.0, 2.0]}) assert gmv(li) == 15.5 def test_resend_is_not_a_repeat(): o = pd.DataFrame({"order_key": ["A1", "a1 ", "B2", "C3"], "customer_key": ["c1", "c1", "c2", "c2"]}) assert repeat_rate(o) == 0.5 for t in [test_resend_counts_once, test_gmv_excludes_freight, test_resend_is_not_a_repeat]: t() print("3 tests passed") # prints: 3 tests passed

Run the registry on the delivered orders, with the person key as the customer. Rename the Olist columns to the schema names from session 1 so the functions never learn a source's spelling.

Compare against the naive definition, on purpose. Agreement is the smaller over the larger, the same measure session 10 prints.

★ Block 4 · the naive GMVnaive = round((li.price + li.freight_value).sum(), 2) print(f"naive price + freight {naive:,.2f} agreement {gmv(li) / naive:.2%}") # prints: naive price + freight 15,419,773.75 agreement 85.74%

Break the grain once, to feel it. Group by the per-order customer id instead of the person and the repeat rate collapses.

Check yourself

Three questions

Clear all three and Builder session 3 gets stamped in your passport.

1 · The naive GMV of Serai's raw exports reads BRL 1,408,548.98 against a reference of BRL 1,197,842.24. What is the main cause?

GMV in the registry is item price only. Freight is charged per item beside the price, so adding it inflates the total; on the full public file that alone gives 85.74% agreement. Re-sends add a little more, but the gap is mainly a definition gap.

2 · Run unchanged on the raw exports, the registry's repeat rate reads 4.61% instead of 3.00%. Where should the fix go?

The definition counted correctly; the rows held re-sends. Patching the definition would also delete Olist's real same-day repeat orders, 83 of 197 in the sample. Session 2's key test drops the re-send, and the registry returns to 100.00% agreement.

3 · Why does the registry report the minimum agreement across its metrics rather than the average?

On dirty rows orders agree at 98.27% and GMV at 99.03%, so an average would hide that the repeat rate is more than half again too high. The weakest metric decides whether the registry can be trusted.
