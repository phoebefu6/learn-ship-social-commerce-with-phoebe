Part 0

From one repeat rate to a repeat shape

Session 3 made repeat rate one tested definition: customers with two or more orders divided by customers. That definition is right for a registry and too blunt for a decision. A seller asking "are the people I won in November coming back?" needs the rate split by when people arrived, and the model in session 5 needs a label that says whether a specific order was followed by another within a fixed window. Both live on the repaired frame from session 2. Part 1 · covers monthly acquisition cohorts and the cohort grid

Monthly cohorts

6 min live

A cohort is everyone whose first delivered order fell in the same month. Each person joins one row for life, and the columns count how many of them ordered again one, two, three months later. The grid answers a question the single rate cannot: is retention getting better for the people you are winning now, or is an old cohort carrying the average?

LiveThree decisions that define a cohort grid4 min▶
DecisionChoice hereWhy
Who is a personthe resolved customer keyOlist's per-order customer id changes every order; counting it makes every buyer a one-timer. Serai's key comes from the identity gate.
What starts a cohortmonth of the first delivered orderThe same frame and status filter as the registry, so the grid's month-0 column adds up to the registry's customer count.
What a cell countsdistinct people with an order in that monthCounting orders lets one heavy buyer fill a cell. People keep the grid comparable with the repeat rate.

On the full public file the build-along finds 96,478 delivered orders from 93,358 people in 23 monthly cohorts. Month 0 across all cohorts adds up to 93,358, the same people the registry counts. That check is the cheapest test of a cohort grid: if month 0 does not reconcile to the registry, the grid and the registry are not using the same definition of a customer.

LiveCounts or shares, and why the small cells matter2 min▶

Divide each row by its month-0 count and the grid becomes shares: 0.44% of the March 2017 cohort ordered again in month 1, 0.62% of April's. Those shares rest on 11 and 14 people. One extra buyer in April moves month 1 by about 0.04 points, which is as large as some of the differences between cohorts. Publish the count beside every share, and do not draw a trend through cells that hold single-digit people.

Self-studyCohort size is a story of its own2 min▶

The month-0 column is acquisition: 717 first-time buyers in January 2017 against 7,060 in November 2017 on the full file. A large cohort won during a promotion often behaves differently from one won in a quiet month, so a falling average repeat rate can be nothing more than a change in the mix of cohorts. Compare cohorts at the same age, never the overall rate across months with different mixes.

Real world

A marketplace where almost nobody comes back. Across all of Olist's delivered orders, 2,801 of 93,358 people placed more than one: 3.00%. Serai's 8,614-order sample was drawn to keep that real ratio, which is why its registry also reads 3.00% (250 of 8,333). In a business like that, a cohort grid is mostly empty cells, and the analyst's job is to stop anyone reading a pattern into two people.

Part 2 · covers the per-order 90-day repeat label and the open window

Repeat within 90 days

6 min live

The cohort grid is about people. The model in session 5 is about orders: at the moment of this purchase, will the same person order again within 90 days? The label is 1 if they did, 0 if the full 90 days passed without another order, and unknown if the 90 days have not passed yet. That third value is the one people forget.

LiveThe label as a rule, written once3 min▶

Sort each person's orders by purchase time. For every order, look at the next order by the same person. If it exists and the gap is 90 days or less, the label is 1. If the gap is longer, or there is no next order and the full 90 days have passed before the data ends, the label is 0. If there is no next order and the data ends inside the 90 days, the label is unknown and the order leaves the training set.

★ The label in one functiondef repeat_90(ts, next_ts, data_end, days=90): window = pd.Timedelta(days=days) if pd.notna(next_ts) and next_ts - ts <= window: return 1 if ts + window <= data_end: return 0 return None # window still open: unknown, not 0

This is the label the bench's model uses. Session 5 trains on orders up to 2017-11-02 so that every label window closes by 2018-01-31, the end of month T, and scores February 2018. On Serai's repaired frame that gives 60 positive labels in 2,744 training orders.

LiveWhy 90 days, and what changes if you pick another number2 min▶

The window is a business choice, not a fact in the data. Shorter windows give more closed labels and fewer positives; longer windows give more positives and push the usable training data further back in time, because more recent orders still have open windows. Pick the window that matches the action the score feeds, write it in the registry beside the definition, and never change it without changing the name. "Repeat within 90 days" and "repeat within 180 days" are two metrics.

Self-studyPer order, per person, per cohort: three repeat numbers3 min▶

The registry's repeat rate is per person over all time: 250 of 8,333 on Serai's frame. The 90-day label is per order: 197 of 8,614 orders are followed within 90 days. The cohort grid is per person per month since first order. All three are correct and none of them equals another. When someone quotes "our repeat rate", the first question is which of the three, over what window. Write the denominator next to every one.

Real world

The last orders in a file always look loyal-less. Olist's public file ends with a purchase on 2018-08-29. An order from mid-August has had two weeks to be followed, not ninety days. Label it 0 and the most recent months look like a retention collapse that never happened. On the full file that is 18,679 orders whose window is still open, about one in five delivered orders.

Part 3 · covers same-day repeat orders and what they do to every repeat number

Same-day repeats

5 min live

Of the 197 orders in Serai's sample that are followed by another within 90 days, 83 are followed on the same calendar day. That is a real Olist pattern, not a defect the builder planted. Some of those are surely people coming back for more. Some may be one shopping trip checked out twice. The rows do not say which, and an honest analyst says so rather than picking the reading that flatters the number.

LiveTeach the ambiguity, publish both numbers3 min▶

On the full public file the build-along prints 2,148 orders followed within 90 days, 890 of them on the same day: 41.4%, close to Serai's 83 of 197. Count people instead of orders and the all-time repeat rate is 3.00% with same-day orders and 2.16% if only orders on two or more distinct days count. Neither is the true repeat rate. One treats every same-day order as a return; the other treats every one as part of the first trip. Publish both, name which one the registry carries, and add a same-day flag to the label table so the model in session 5 can be checked with and without them.

LiveWhy a re-send hides here2 min▶

A re-sent order arrives on the same day, for the same customer, under a variant key. On a frame that has not been through session 2's checks it is indistinguishable from a same-day repeat. That is exactly what the bench shows when the data engineering layer is skipped: the registry counts 384 repeat customers instead of 250 and the repeat rate reads 4.61% instead of 3.00%, with agreement on repeat rate down to 65.14%. The model's training set grows from 60 positive labels to 108. Real same-day repeats make the fake ones look plausible, which is why the key check has to run before any repeat number is computed, not after.

Self-studySame-day orders and the review score2 min▶

Olist's satisfaction survey goes out once the customer receives the product or the estimated delivery date is due. A same-day repeat is placed before any review of the first order can exist. So review score cannot explain a same-day return, and any feature built from it would be using information from after the purchase. Session 5 leaves review score out of the model for that reason, and session 6 treats it as a timing leak.

Real world

A pattern that survives every sample. Same-day follow-ups are 83 of 197 repeats in Serai's seeded sample and 890 of 2,148 on the full public file: roughly two in five both times. When a pattern holds at that share in a random sample and the whole population, it is a property of how people buy on the marketplace, and every repeat definition downstream has to take a position on it.

Build-along

The cohort grid and the 90-day label, in pandas

★ 22 min · everyone builds

Download the public dataset with kagglehub.dataset_download("olistbr/brazilian-ecommerce") (no login needed) and run each block in order from a scratch folder. The outputs below are what these exact blocks print on the full file. Serai's bench runs the same logic on its seeded 8,614-order sample, so its counts are smaller.

Load delivered orders with the person key. Point d at the downloaded folder. The person is customer_unique_id, not the per-order customer_id.

★ Block 1 · loadimport pandas as pd d = "path/to/olist/" orders = pd.read_csv(d + "olist_orders_dataset.csv", parse_dates=["order_purchase_timestamp"]) cust = pd.read_csv(d + "olist_customers_dataset.csv") o = (orders[orders.order_status == "delivered"] .merge(cust[["customer_id", "customer_unique_id"]], on="customer_id") .rename(columns={"customer_unique_id": "person", "order_purchase_timestamp": "ts"}) [["order_id", "person", "ts"]]) print("orders", len(o), "people", o.person.nunique()) # prints: orders 96478 people 93358

Build the cohort grid of distinct people. The cohort is each person's first month; the age is months since it.

★ Block 2 · the grido["month"] = o.ts.dt.to_period("M") o["cohort"] = o.groupby("person").month.transform("min") o["age"] = (o.month - o.cohort).apply(lambda p: p.n) grid = o.groupby(["cohort", "age"]).person.nunique().unstack(fill_value=0) print(grid.loc["2017-01":"2017-06", 0:3]) print("cohorts", len(grid), "| 2017-11 cohort size", grid.loc["2017-11", 0]) # prints: # age 0 1 2 3 # cohort # 2017-01 717 2 2 1 # 2017-02 1628 3 5 2 # 2017-03 2503 11 9 10 # 2017-04 2256 14 5 4 # 2017-05 3451 16 16 10 # 2017-06 3037 15 12 13 # cohorts 23 | 2017-11 cohort size 7060

Turn counts into shares, and keep the counts beside them.

★ Block 3 · sharesshare = grid.div(grid[0], axis=0) * 100 print(share.loc["2017-01":"2017-06", 1:3].round(2)) # prints: # age 1 2 3 # cohort # 2017-01 0.28 0.28 0.14 # 2017-02 0.18 0.31 0.12 # 2017-03 0.44 0.36 0.40 # 2017-04 0.62 0.22 0.18 # 2017-05 0.46 0.46 0.29 # 2017-06 0.49 0.40 0.43

Label every order: is the same person's next order within 90 days? Sorting by order id after time makes ties deterministic.

★ Block 4 · the 90-day label and the same-day flago = o.sort_values(["person", "ts", "order_id"]) o["next_ts"] = o.groupby("person").ts.shift(-1) o["rep90"] = (o.next_ts - o.ts) <= pd.Timedelta(days=90) o["same_day"] = o.rep90 & (o.next_ts.dt.date == o.ts.dt.date) print("followed within 90 days", o.rep90.sum(), "| same day", o.same_day.sum(), f"| share {o.same_day.mean() / o.rep90.mean():.1%}") # prints: followed within 90 days 2148 | same day 890 | share 41.4%

Find the orders whose window has not closed. These are unknown, not 0. Drop them from any training set or retention rate that uses the 90-day label.

★ Block 5 · open windowslast = o.ts.max() open_window = o.ts > last - pd.Timedelta(days=90) print("last purchase", last.date(), "| windows still open", open_window.sum()) # prints: last purchase 2018-08-29 | windows still open 18679

Print the repeat rate both ways. One line for the registry's definition, one for the distinct-day reading.

★ Block 6 · with and without same-day ordersper = o.groupby("person").agg(n=("order_id", "size"), days=("ts", lambda s: s.dt.date.nunique())) print(f"repeat rate {(per.n > 1).mean():.2%} ({(per.n > 1).sum()} of {len(per)})") print(f"repeat on 2+ distinct days {(per.days > 1).mean():.2%} ({(per.days > 1).sum()})") # prints: repeat rate 3.00% (2801 of 93358) # repeat on 2+ distinct days 2.16% (2015)

Write the window and the same-day choice at the top of the file. One comment: "repeat_90 = next order by the same person within 90 days of purchase; open windows are unknown; same_day kept as a flag". Session 5 reads that comment before it trains anything.

The label that quietly calls the last 90 days a collapse o["label"] = o.rep90.astype(int) # open windows become 0: every August 2018 order "never came back"

Check yourself

Three questions

Clear all three and Builder session 4 gets stamped in your passport.

1 · A cohort grid counts distinct people per first-purchase month and months since. Which check tells you the grid and the registry agree on what a customer is?

Each person sits in exactly one row, so month 0 must add up to the number of distinct people: 93,358 on the full file. If it does not, the grid is using a different key or filter from the registry. Shares need not fall monotonically, and small cells often do not.

2 · The file ends on 2018-08-29. An order placed on 2018-08-10 has no later order by the same person. What is its 90-day repeat label?

Only 19 of its 90 days have passed. Calling it 0 makes recent months look like a retention collapse. That is why session 5 trains on orders up to 2017-11-02, so every window closes by 2018-01-31. On the full file, 18,679 orders sit in that open stretch.

3 · 83 of Serai's 197 repeats within 90 days are same-day. What is the honest way to report repeat purchase?

The rows carry no basket id, so a split basket and a real return look the same. Dropping them assumes one reading, keeping them silently assumes the other, and averaging hides both. On the full file the two readings are 3.00% and 2.16%; show both and let the definition be a visible choice.
