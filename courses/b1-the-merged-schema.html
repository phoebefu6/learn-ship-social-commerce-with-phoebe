Part 1 · covers tables, grain and what each table is for

Declare the grain before the columns

6 min live

The grain is the sentence "one row per ___". Write it at the top of every table before choosing a single column. Most silent errors in commerce data are two tables of different grain joined as if they were the same.

Olist's own documentation warns that an order may have multiple items and each item may be fulfilled by a distinct seller. That is why store lives on lines, not on orders: an order does not have one store. In Serai's sample 39 orders carry more than one review, and 68 carry none. The schema keeps every review row; the order-level fact table keeps the first by answer time and says so.

LiveWhat goes in the schema, and what stays out3 min▶

In: order status and timestamps, the export each row came from, prices and freight in the smallest currency unit, payment type and instalments, review scores, store and product keys. Out: anything the later layers do not consume and the licence does not allow you to ship. Olist's review text is CC BY-NC-SA licensed, so Serai's shipped data carries scores only. Masking is a schema decision, not a later clean-up: the builder renumbers customers by first appearance and stores by frequency, so no source id leaves the script.

Real world

A dataset that documents its own traps. The Olist dataset description lists, in its "Attention" notes, that an order might have multiple items and that each item might be fulfilled by a distinct seller. Most commerce sources say nothing of the kind, and the first sign of a multi-seller order is a GMV figure that looks too high. Write the grain down even when the source does not.

Part 2 · covers three exports mapped into one shape

Three exports, one shape, one column of provenance

6 min live

Each marketplace export has its own column names and its own habits. The merged schema maps every export to the same tables, normalises the order key, and keeps a column saying which export each row came from, so the tests in session 2 can report a pass rate per source.

LiveThe mapping contract, one block per export3 min▶

Write the mapping as data, not as code scattered through a notebook: for each export, which source column feeds which schema column, the unit it arrives in, and the key normalisation rule. The Enablers course designs the three-export schema and the masking rules each export applies (Analyst session 2 there); this session takes that design as given and builds it.

★ A mapping contract, as dataEXPORT_MAP = { "Export A": {"order_key": "order_id", "price_cents": ("item_price", 100), "ts_purchase": "created_at"}, "Export B": {"order_key": "OrderNo", "price_cents": ("price_brl", 100), "ts_purchase": "order_time"}, "Export C": {"order_key": "order_ref", "price_cents": ("amount", 100), "ts_purchase": "placed"}, } KEY_RULE = "strip whitespace, lower-case, drop a trailing '-r' re-send suffix"

The column names above are illustrative; every marketplace names them differently, and the point is that the contract lives in one place the tests can read.

Self-studyMoney in the smallest unit, time in one zone2 min▶

Store money as integer cents. Floats add rounding noise that turns "agrees to the cent" into "agrees to within 0.0000001", and the registry in session 3 depends on exact agreement. The Serai builder stores every price and freight in cents and checks that the integer total, 119,784,224 cents, matches the float total from the source within one cent. Store timestamps in one zone and keep the raw value beside any derived day: the 122 real Olist orders whose carrier pickup precedes payment approval are only visible if both timestamps survive.

Part 3 · covers the fan-out join and the order-level fact table

Roll up first, then join

5 min live

Join lines to payments on the order key and every line is repeated once per payment. Sum the price and you have counted some items twice. Nothing fails: the join is valid SQL and valid pandas. The fix is a rule, not a trick: roll every child table up to the order grain, then join.

LiveThree assertions that make a fan-out impossible to miss3 min▶

After building the fact table, assert three things and let the script stop if any fails: the row count equals the number of distinct delivered order keys; the order key is unique; the summed item value equals the sum of the line prices before any join. The third one is the fan-out detector. It costs one line and it catches every join that multiplies rows, including the ones added by a colleague six months later.

★ The three assertionsassert len(fact) == o.order_id.nunique() assert fact.index.is_unique assert round(fact.price.sum(), 2) == round(li.price.sum(), 2)
Self-studyWhere the customer key comes from3 min▶

Olist ships a per-order customer id and a customer_unique_id for the person behind it; 96,478 delivered orders belong to 93,358 unique people. Serai's real exports carry three masked keys that do not match each other, and the Enablers course builds the identity gate that resolves them (Analyst session 3 there). This track takes the gate's output as the customer key. When an export sends a key the customer table has never seen, as 113 rows on Serai's bench do, the merged schema resolves it through the gate's crosswalk; session 2 turns that into a test.

★ Block 3 · the fan-out, deliberatelywrong = li.merge(pa, on="order_id")["price"].sum() right = li["price"].sum() print(f"item value right {right:,.2f} after joining payments {wrong:,.2f} inflation {wrong / right - 1:.2%}") # prints: item value right 13,221,498.11 after joining payments 13,813,828.71 inflation 4.48%

Roll each child table up to order grain, join, and assert. Keep the first review by answer time, and say so in a comment, because that choice changes the review facts session 7 checks.

★ Block 4 · the fact tablelines_o = li.groupby("order_id").agg(items=("order_item_id", "size"), price=("price", "sum"), freight=("freight_value", "sum")) pays_o = pa.groupby("order_id").agg(paid=("payment_value", "sum"), installments=("payment_installments", "max")) rev_o = rv.sort_values(["order_id", "review_answer_timestamp", "review_id"]).groupby("order_id").review_score.first() # first review per order fact = o.set_index("order_id").join(lines_o).join(pays_o).join(rev_o) assert len(fact) == o.order_id.nunique() assert fact.index.is_unique assert round(fact.price.sum(), 2) == round(li.price.sum(), 2) print("fact rows", len(fact), f"item value {fact.price.sum():,.2f}", "orders with no review", fact.review_score.isna().sum()) # prints: fact rows 96478 item value 13,221,498.11 orders with no review 646

Check yourself

Three questions

Clear all three and Builder session 1 gets stamped in your passport.

1 · Why does the store key live on the lines table rather than on orders?

Olist's own notes say each item may be fulfilled by a distinct seller. Putting store on orders forces a choice of one seller per order and silently misattributes the rest.

2 · Joining lines to payments and summing price gives BRL 13,813,828.71 against BRL 13,221,498.11. What happened?

A one-to-many joined to a one-to-many multiplies rows. 2,875 delivered orders have more than one payment row. Roll both tables up to order grain first and the total equals the sum of line prices.

3 · Which assertion catches a fan-out join that a colleague adds six months from now?

A fan-out raises no error and leaves no gaps; it only changes totals. Comparing a total against an independent sum is the check that sees it. The row-count and unique-key assertions catch the cases where it adds rows.
